## 0. בקשת ZDR
כל הפרטים והמייל באנגלית: [`external/ZDR_REQUEST.md`](external/ZDR_REQUEST.md). אור שולח, עינת בהעתק. כשמגיעה תשובה: הצעדים בסוף אותו קובץ, ועינת מסמנת את הפריט הראשון ב"מוכנה לתיקים אמיתיים?".

## 1. אפליקציית גוגל: לצאת ממצב Testing
**למה עכשיו:** בגרסה הקרובה ערכת השחזור המודפסת כבר לא מוצעת בהגדרה הראשונה, ו**כניסה עם גוגל היא הדרך העיקרית של עינת לחזור לכספת** כשהיא שוכחת סיסמה (D-041). במצב Testing:
- רק חשבונות שברשימת Test users יכולים להיכנס, וגוגל מציגה מסך "האפליקציה לא אומתה".
- ה-refresh token של העותק המוצפן בדרייב (D-099) פג אחרי 7 ימים, ולכן המתג יבקש "חיבור מחדש" כל שבוע. זה הפריט שמסומן "[דורש את אור]" ב-D-099.

**הצעדים** (Google Cloud Console, הפרויקט שנוצר לפי `RELEASE_HE.md` §"כניסה עם גוגל"):
1. **דף מדיניות פרטיות.** גוגל דורשת קישור לדף ציבורי. המקום הפשוט: GitHub Pages בריפו ההתקנות הציבורי (`orliber/einat-vault-releases`), קובץ `privacy.html`. מה כתוב בו, בעברית ובאנגלית: התוכנה מבקשת רק `openid` ו-`drive.appdata`; היא שומרת בתיקייה הנסתרת של האפליקציה קובץ אחד עם חצי ממפתח אקראי, ואם המשתמשת הדליקה, גם עותקים מוצפנים של הגיבוי; היא לא קוראת שום קובץ אחר בדרייב, לא שולחת מידע לשרת שלנו (אין כזה) ולא משתפת מידע עם אף אחד. בלי שמות, בלי פרטים על מטופלים.
2. **Google Auth Platform ← Branding** (בעבר "OAuth consent screen"): שם "כספת האבחון", מייל תמיכה, דף הבית (דף הריפו הציבורי), הקישור למדיניות, ו-Authorized domains לדומיין של הדפים. **לא מעלים לוגו**: לוגו מחייב אימות מותג (brand verification) ועיכוב.
3. **Data Access:** לוודא שברשימה יש רק `openid` ו-`.../auth/drive.appdata`. שתיהן לא רגישות אצל גוגל (non-sensitive), ולכן לא אמור להידרש אימות של הרשאות רגישות או בדיקת אבטחה. אם מופיעה הרשאה נוספת, מוחקים אותה.
4. **Audience ← Publishing status ← Publish app** (מעבר ל-In production). אם גוגל מבקשת אימות: ממלאים את מה שמבקשים, ומוסיפים בינתיים את החשבון של עינת ל-Test users כדי שהיא לא תיתקע.
5. **Clients:** לוודא שה-client הוא מסוג Desktop app, ושהסודות `DV_GOOGLE_CLIENT_ID` ו-`DV_GOOGLE_CLIENT_SECRET` בריפו לא השתנו. אין צורך בגרסה חדשה.

**איך יודעים שעבד:**
- בכספת בדויה, כניסה עם גוגל מחשבון שלא ברשימת Test users עוברת בלי מסך "לא אומתה".
- אחרי 8 ימים עם העותק בדרייב דלוק (בכספת בדויה), גיבוי עדיין עולה בלי "חיבור מחדש".
- רושמים ב-`DECISIONS.md`: "האפליקציה אצל גוגל פורסמה, תאריך".

## 2. חתימת קוד ל-Windows
**למה:** בלי חתימה Windows מציג "Windows protected your PC" ו-SmartScreen, אין שם מאומת על המתקין, ומבדק החדירה יסמן את זה (`PENTEST_SCOPE.md` §8, `STANDARDS.md` §5.8). העדכון בתוך התוכנה כבר מוגן בחתימה משלו (D-033), אבל ההתקנה הראשונה לא.

**איזו תעודה (המחמירה שזמינה):**
- **Azure Artifact Signing** (לשעבר Trusted Signing) של Microsoft זמין היום ליחידים רק בארה"ב ובקנדה, ולארגונים בארה"ב, קנדה, האיחוד האירופי ובריטניה. לעוסק בישראל הוא לא זמין, אלא אם יש חברה רשומה באחת המדינות האלה.
- **נבחר: תעודת OV** (Organization Validation) על שם עינת או הקליניקה, מרשות מוכרת עם **חתימה בענן**, כך שהמפתח נשאר ב-HSM של הרשות ולא יוצא אף פעם (זו גם דרישת התעשייה מאז 2023). דוגמאות: SSL.com eSigner, DigiCert KeyLocker, Sectigo, Certum. משווים מחיר ותמיכה בחתימה מ-GitHub Actions.
- תעודת EV מחייבת חברה רשומה, ומאז 2024 כבר לא נותנת ל-SmartScreen אמון מיידי יותר מ-OV. אם יש חברה, EV מחמירה יותר באימות הזהות, ואפשר לבחור בה.

**הצעדים:**
1. קונים תעודה, ועוברים אימות זהות (תעודה מזהה, ואם על שם עסק: מסמכי העסק). השם שמופיע בתעודה הוא מה שעינת תראה בחלון ההתקנה.
2. בחשבון החתימה בענן: אימות דו-שלבי, משתמש ייעודי לחתימה מ-CI.
3. ב-GitHub: Settings ← Environments ← `release`, עם **אישור ידני** (Required reviewers: אור), ובתוכו הסודות של שירות החתימה. הם זמינים רק לשחרור, לא לכל PR.
4. **שינוי בקוד, ב-thread נפרד של Claude** (עם החלטה חדשה ב-`DECISIONS.md`): לחתום ב-`release.yml` (שם נעשה היום רק חיתום ההודעה) את כל קובצי ההפעלה שנארזים, לא רק את המתקין: `DiagnosticVault.exe`, ה-DLL של מודול ה-FIPS, Tesseract, ואז את מתקין ה-NSIS. SHA-256 עם חותמת זמן RFC 3161. אחרי החתימה מחשבים מחדש את ה-`.sha256` ואת הודעת העדכון (D-033), כי החתימה משנה את הבתים. ה-CI על `main` ממשיך לבנות בלי חתימה.

**איך יודעים שעבד:** `signtool verify /pa /all /v` עובר על כל קובץ, בתוך ה-workflow; בחלון ההתקנה מופיע השם המאומת; עדכון מגרסה קודמת עובר (ה-SHA-256 בהודעה תואם לקובץ החתום).

## 3. חתימה ואימות ל-Mac
**למה:** היום האפליקציה חתומה ad-hoc. Gatekeeper מציג "Open Anyway" בפעם הראשונה, ובלי Team ID נדרשה ב-0.8.1 ההרשאה `disable-library-validation` כדי שמודול ה-FIPS ייטען (D-101). חתימת Developer ID מאפשרת להוריד את ההרשאה הזו ולהחזיר את הבדיקה.

**הצעדים:**
1. הרשמה ל-Apple Developer Program (99$ לשנה). כיחיד מספיק Apple ID עם אימות דו-שלבי; כארגון צריך מספר D-U-N-S. השם שמופיע ב-Gatekeeper הוא שם החשבון.
2. ב-Certificates: יוצרים **Developer ID Application** (רק Account Holder יכול), ומייצאים `.p12` עם סיסמה.
3. ב-App Store Connect ← Users and Access ← Integrations: מפתח API ל-notarization (Issuer ID, Key ID, קובץ `.p8`).
4. ב-GitHub, ב-Environment `release` (כמו ב-2): `APPLE_CERTIFICATE` (ה-`.p12` ב-base64), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY`, `APPLE_API_ISSUER`, `APPLE_API_KEY`, ותוכן ה-`.p8`. אלה השמות ש-Tauri קורא.
5. **שינוי בקוד, ב-thread נפרד של Claude:** `signingIdentity` במקום `"-"`, חתימה של מודול ה-FIPS באותה זהות, **הסרת `com.apple.security.cs.disable-library-validation`** מ-`macos/Entitlements.plist` (D-101, חלופה א), notarization ו-staple לדמות, וחישוב ה-CDHash **אחרי** החתימה (ההודעה החתומה מקבלת רק אותו). בהמשך, לפי D-101: Secure Enclave ו-App Sandbox.

**איך יודעים שעבד:** `spctl -a -vv` מחזיר `accepted, source=Developer ID`; `xcrun stapler validate` עובר על הדמות; האפליקציה נפתחת ב-Mac אחר בלי "Open Anyway"; עדכון מ-0.8.x עובר.

## 4. מבדק חדירה חיצוני
**למה:** תנאי לתיק אמיתי (`STANDARDS.md` §5.1). ההיקף המלא כבר כתוב: [`external/PENTEST_SCOPE.md`](external/PENTEST_SCOPE.md).

**הצעדים:**
1. **אחרי 2 ו-3**, על הגרסה שתותקן אצל עינת. מבדק על גרסה שעוד משתנה לא שווה את הכסף.
2. לסגור קודם מה שאפשר מ-`PENTEST_SCOPE.md` §8 (פתוח היום: חתימת קוד, ונעילה בנעילת מסך בלי שינה).
3. לשלוח את `PENTEST_SCOPE.md` לשתיים-שלוש חברות, עם השאלות שבסעיף 10 שלו, ולבקש הצעת מחיר שכוללת בדיקה חוזרת, מכתב אישור וסיכום בעברית לעינת.
4. לפני שמתחילים: NDA והרשאת בדיקה בכתב (שאלה 26 לעו"ד), ארגון נפרד ב-Anthropic עם תקרת הוצאה נמוכה ומפתח שמבוטל בסוף, ו-snapshot של ה-commit שממנו נבנה המתקין.
5. ממצא קריטי (דליפת מזהה, עקיפת השער) מתוקן מיד, לא בסוף המבדק.
6. אחרי הבדיקה החוזרת: הדוח והמכתב נשמרים **מחוץ לריפו**. בריפו רושמים ב-`DECISIONS.md` רק את המסקנה ואת התאריך, וקובעים את המבדק הבא (כל 18 חודשים, ואחרי כל שינוי מהותי ב-`dv-privacy`, `dv-egress` או `dv-vault`).

**איך יודעים שעבד:** מכתב מהחברה שהבדיקה החוזרת עברה בלי ממצא קריטי או גבוה פתוח.
